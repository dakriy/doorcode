# AGENTS.md

This file is the contract for anyone changing this repository. The first half
is the standing methodology and is identical across repositories. The second
half is project-specific. Where a project-specific section records a
deviation, the deviation wins for the scope it names.

> Effects behind connectors. Tests through the real entrypoint. Everything
> else is verified by the build.

## Judgment rules

These are the rules the build cannot check. Hold them in mind while coding.

1. **Effects go behind connectors.** Anything that touches the outside world
   or is nondeterministic is reached only through a connector interface:
   network, storage, processes, environment, clock, randomness, identifier
   generation. A connector interface is narrow and named for what the
   application needs, never a pass-through for the external protocol; a
   method that accepts raw SQL or a raw URL moves the query logic into
   application code where no test can see whether it is right. The
   implementation is as thin as the external API allows, reports what the
   system said in whatever types are natural, and makes no decisions: no
   branching on content, no defaults, no interpretation of codes or absences.
   A generator seeded from an explicit input is pure and is not a connector;
   the seed's source is.
2. **Production wiring is the only place real connectors are built.** A
   connector factory interface has one method per connector and nothing else,
   never a plain value. The production factory lives with `main` and does
   nothing but construct real connectors and call the entrypoint. The stub
   factory lives in test support. The entrypoint takes the factory and never
   constructs a connector itself, so everything from the entrypoint inward is
   tested.
3. **Tests enter at the real entrypoint and assert on outcomes.** Every test
   of application code calls the entrypoint with the stub factory. It asserts
   on results, state, what the stubs recorded, and errors. Never on which
   internal function ran, how often, or in what order. One behavior per test,
   named for the behavior. Stubs are hand-written connector implementations in
   test support; nothing else is ever replaced, and no mocking library exists
   in the repository. There are no unit tests of internals.
4. **No test asserts absence.** Not that a symbol, import, or feature does
   not exist, not that a call was not made, not that output is empty with
   nothing else said. Assert the outcome that does happen. Absence of code is
   the dead-code check's job.
5. **The test DSL grows from repetition.** Extract shared setup on the third
   occurrence, in the language of the product, with no hidden assertions and
   no tests of its own.
6. **Wire it or delete it.** Production code with no caller reachable from an
   entrypoint does not ship. Create abstractions after a pattern exists, not
   before.
7. **Boring, immutable code.** A reader follows any function top to bottom
   without decoding it: plain loops, named intermediates, early returns, the
   obvious language feature. Produce new values rather than mutating, unless
   the reason is visible at the site. Repeat text, not knowledge: extract
   shared code on the third occurrence and only when the copies encode the
   same decision.
8. **Done means verified, and no mutant survives.** `verify-fast` green after
   every change. `verify-mutation` green whenever application code changed,
   and green means an empty survivor list: every survivor the run produced
   was killed by a stronger test, removed with the over-defensive code it
   lived in, or suppressed as equivalent with a written reason.
   `verify-integration` green only when a connector changed. A verification
   not run is reported as not run. No gate is lowered and no allowlist
   widened to make a change pass.

## What the build enforces

Consult this when a gate fails.

Two kinds of production code exist. **Application code** is everything that
is not a connector implementation or production wiring, entrypoints included.
**Connector code** is connector implementations and the production factory,
verified by connector tests rather than by the coverage and mutation gates.

| Gate | Fails when | Configured under |
| --- | --- | --- |
| Application imports | application code imports a connector implementation, the production wiring, or an effect package | Effect packages |
| Effect calls | application code reads the clock, entropy, or the environment directly, where the linter can see it | Stack |
| Entrypoint-suite imports | an entrypoint test imports anything but entrypoint packages, test support, and listed test libraries | Fast-suite dependencies |
| Coverage | any application function is below 100% line coverage from the entrypoint suite; generated code is excluded by path | Generated code |
| Mutation | any mutant in application code survives, is not covered, or times out | Mutation exclusions |
| Complexity caps | an application function exceeds the application cap, or a connector function exceeds the lower cap | Complexity caps |
| Dead code | production code is unreachable from every entrypoint, where the ecosystem has a tool | Known gaps if none |
| Runtime budget | `verify-fast`'s tests run longer than the budget | Commands |
| Slow-test placement | a connector test marked slow is reached by `verify-fast` | Layout |
| Integration compile | the slow connector tests do not compile or type-check | Commands |
| Static analysis, formatting | the stack's own linter or formatter objects | Stack |
| Duplicate-code report | never; it prints repeated blocks in production code for the next audit | Stack |

## The suites

The **entrypoint suite** runs the real entrypoint against connector stubs. It
is the only test suite for application code, the only source of coverage,
and what mutation testing exercises.

The **connector suite** tests connector implementations against real
systems, local wherever possible: a temp directory, an in-process database, a
container. The same tests also run against the stubs. Each connector test is
marked fast or slow. Fast ones
run in `verify-fast` under the runtime budget; slow ones run only in
`verify-integration`. A connector test that cannot be made fast is slow, not
skipped. Nothing in either suite touches a production system. A system that
cannot run locally is either mimicked by a local service or represented only
by stub data, with no integration test.

The runtime budget covers everything `verify-fast` runs.

| Command | Runs | When |
| --- | --- | --- |
| `verify-fast` | every gate above except mutation; the entrypoint suite and the fast connector tests | after every change |
| `verify-mutation` | mutation testing of application code, survivor report | before finishing an application-code change |
| `verify-integration` | the slow connector tests | only when a connector interface or implementation changed, and on a schedule in CI |
| `verify-all` | all three, stopping at the first failure | before release or on request |

# Project-specific

## Stack

- Language and version: Go 1.27 (module `github.com/dakriy/doorcode`)
- Build system: the Go toolchain; GNU Make as the task runner. Every tool is pinned as a `tool` directive in `go.mod` and run with `go tool`, so the only host requirements are Go, Make, and a POSIX shell.
- Test framework: the standard `testing` package
- Assertion library with diff output: `github.com/google/go-cmp/cmp` (`cmp.Diff`)
- Coverage tool: `go test -coverpkg=<application packages> -coverprofile`, gated by `scripts/coverage-gate.sh` over `go tool cover -func`
- Mutation tool: gremlins v0.6.0 in `--integration` mode, gated by `scripts/mutation.sh` on the survivor list
- Import-rule tool: depguard via golangci-lint v2.15.0 (`.golangci.yml`)
- Effect-call linter: forbidigo via golangci-lint (`.golangci.yml`)
- Dead-code tool: `golang.org/x/tools/cmd/deadcode`, wrapped by `scripts/deadcode.sh`
- Duplicate-code tool: dupl via golangci-lint (`.golangci.dupl.yml`, threshold 50 tokens, reporting only)
- Database: PostgreSQL 18 through pgx v5 (`github.com/jackc/pgx/v5`); schema migrations are embedded SQL files run by tern v2 (`github.com/jackc/tern/v2/migrate`) from the store's `Migrate`
- Password hashing: argon2id (`golang.org/x/crypto/argon2`) in PHC string format, in `internal/auth`. The salt comes from the Entropy connector, so hashing is pure; the memory cost is the `password_hash_memory_kib` setting.
- Web UI: `html/template` pages and static assets embedded from `internal/app/ui`; htmx v2.0.10, Swagger UI 5.34.0 (`swagger-ui-dist` from npm), FullCalendar 6.1.22 (`fullcalendar` from npm, its standard global bundle, for calendar views), and the Tailwind CSS v4.3.3 standalone CLI, all pinned with SHA-256 checksums in `scripts/vendor-ui.sh` (`make ui`). The built `internal/app/ui/static/app.css`, the vendored `htmx.min.js`, `internal/app/ui/static/swagger-ui/` (bundle, stylesheet, license), and `internal/app/ui/static/fullcalendar/` (bundle, license) are committed; the CLI is cached under `build/tools` and never committed. No Node, no package.json. Dark mode is Tailwind's default `dark:` variant, which follows `prefers-color-scheme`.
- JSON API: every route, page or `/api/v1` operation, is one entry of the route table in `internal/app` (`(*App).routes`, assembled from per-feature functions such as `settingsRoutes` and `tokenRoutes`; `pageRoute` and `apiRoute` build entries). The mux and the OpenAPI 3.1 document are both built from it; there is no other registration path. An API entry carries an `apiDoc` (operationId, summary, tag, `openapi.Param`s with examples, an example request body or a `form` value whose type describes a multipart body, responses with a value of each body's wire type; `openapi.File` is a binary field or body and `Response.Type` names a body's media type when it is not JSON); the access check adds 401, 500, and, for a role, 403. `internal/openapi` derives schemas by reflection from json tags (`omitempty` makes a field optional; a `doc` tag is its description). The document is served at `/api/v1/openapi.json`, rendered by Swagger UI at `/api-docs`, and checked in at `docs/openapi.json`.
- API authentication: personal API tokens (`dct_` plus 32 entropy bytes, stored as a SHA-256 hash, optional expiry) in `Authorization: Bearer` or as the HTTP Basic password; an Authorization header that carries one wins over the session cookie, which is still accepted so the browser's own calls work.
- Time zones: the tz database reaches the application only through the `TimeZones` connector. Its driver, `internal/driver/tzdb`, calls `time.LoadLocation` and imports `time/tzdata`, so the binary carries the database and zones load on hosts without zoneinfo files. The `site_timezone` setting must name a zone it loads (not empty, not `Local`); `settings.Current().Zone` is the loaded zone. Schedule windows are read in it, and dates typed on pages are the start of that day in it.
- Pictures: `internal/picture` decodes JPEG, PNG, GIF (standard library) and WebP (`golang.org/x/image/webp`), scales with `golang.org/x/image/draw` (CatmullRom), flattens transparency onto white, turns the image upright as its EXIF orientation tag says (read with `github.com/rwcarlsen/goexif`, pure Go, pinned in `go.mod`; `orientation` reads 1 to 8, or 1 when the tag is missing, not a single short, or unreadable, and `upright` applies the `turns` table of swap and flips to the fitted image), and re-encodes as JPEG: an image at most `MaxSide` (1600) pixels on its longest side and a thumbnail at most `ThumbnailSide` (320). All pure Go, no cgo. An upload is at most `MaxBytes` (10 MB) and `MaxPixels` (40 million, read from the header before decoding). The app reads the `picture` field of a multipart body with `MultipartReader` in memory, never through `ParseMultipartForm`, which spools to disk. Both renditions are stored as `bytea` behind `PicturesStore` and served from `/api/v1/doors/{id}/pictures/{picture}` (and `/thumbnail`) with `Cache-Control: private, max-age=31536000, immutable`; pages use those URLs as image sources, since the API accepts the session cookie.
- Calendar views: a page lists its intervals in labelled tables, which the entrypoint suite reads, and hands the same intervals to FullCalendar as local wall-clock times without an offset (`data-events`, each with a `title` and a `kind`: `open`, `locked`, `access`, or `code`, which `ui/static/calendar.js` turns into a `calendar-<kind>` class colored in `ui/tailwind.css`); the calendar runs with `timeZone: "UTC"` so it draws them as given, whatever the browser's zone. Calendar pages share the `week` value (`(*App).weekOf`) and the `week-nav`, `calendar`, `calendar-key` (given `calendarkey "Your"|"Their" kinds...`, the viewpoint naming whose code works, in a list labelled `Calendar key`), and `calendar-scripts` parts, and those showing a door's timeline the `span-table` part. A calendar is a page of its own (schedule, door timeline, a user's access at a door), never part of a page reached through htmx, and a link to one sets `hx-boost="false"` so its scripts load in order.
- Timelines: `internal/timeline` is pure. `Merge` turns open-mode intervals and overrides into ordered spans tagged `open` or `locked` (locked overrides win over open overrides, which win over schedules; gaps are the normal code-access state), `OpenScheduleIDs` is the open-mode schedules a door has through its zones (every zone it is in, joined), `Of` expands those first, and `CodeWorks` is when granted intervals open a door given its spans (never while locked). Open mode belongs to zones (`StoredZone.OpenScheduleIDs`); doors carry none of their own. `door.Service.Timeline` loads what `Of` needs. `rule.Service.Affected` names the doors that are not deleted whose timeline depends on a schedule (the doors in a zone in open mode during it), an override (its door), or a zone (its doors) as things stand; access rules and groups decide who may enter, never when a door is open or locked, so changing them sends no timeline. Every change to a schedule, an override, or a zone goes through `affecting` (or `removing`) in `internal/app/pushes.go` (`newZone`, `changeZone`, `removeZone` for zones), which reads the set before and after the change and sends those doors new timelines; a change to a door's zones sends that door its timeline (`changeDoor`). It is not exposed in the API.
- Door configuration: `internal/settings/doors.go` defines every field once in `settings.DoorFields` (name, label, hint, default, parser). Each field's site default is the setting `door_<name>` (so `DOORCODE_DOOR_<NAME>` overrides it); a door's overrides are `StoredDoor.Config`, field name to string value, checked by `settings.CheckOverrides` and stored only through `DoorsStore.SetDoorConfig` (`door.Service.Configure`). `settings.DoorDefaults.For` merges defaults and overrides into a `settings.DoorConfig`, whose fields match `protocol.DoorConfig` and the API's `doorConfigView` so each converts to the other. The code length ranges (shortest 1 to 16, longest 16 to 64) meet without overlapping, so no cross-field check is needed. The settings page edits every setting the environment does not provide in one form (`settings.Service.UpdateAll`, which stores only changed values); a door's page shows its configuration once a controller is enrolled, with a form of overrides (empty follows the default); the API is `GET`/`PUT /api/v1/doors/{id}/config`.
- Pushes: `internal/push` publishes, retained, each door's effective configuration (`doorcode/doors/<id>/config`) and its timeline for the next 25 hours (`doorcode/doors/<id>/timeline`) to every door a controller is enrolled as that is not deleted, connected or not, so a reconnecting controller finds them current (rewriting retained messages of offline doors costs a few publishes on a rare change; pushing only to online doors would leave a stale retained message until the server sees the door come online). A door is sent both when it comes online (`controller` calls `push.Service.Connected`); its timeline when `affecting` names it, when its zones change, and when the site timezone changes (every door); its configuration when its overrides or any `door_` default change (every door). `push.Sent` remembers in memory when each door was last sent its timeline; the periodic work sends it again once its `timeline_refresh_hours` have passed, and after a restart sends every door at once. A failed push is logged (`could not send doors what changed`) and the change stands.
- Code checks: `internal/decision` is the decision chain of spec section 2, in order: the door's token bucket (`decision.Limiter`, in memory, used only by the broker loop; it holds the door's `rate_limit_burst` and refills at its `rate_limit_per_minute` from the Clock; an empty bucket denies `rate limited` without looking the code up), an expired or deleted known user (`auth.AccountEnded`), a keypad command (`<code>*00` then `1<minutes>` open, `2<minutes>` locked, minutes 1 to 1440, or `0` to cancel the overrides in force; only for door commanders, else `not a commander` or `bad command`), a door commander (`auth.UserOf(u).Has`), a locked then an open override in force, the open-mode schedules of the door's zones (`timeline.OpenScheduleIDs`; unknown codes included), an access rule naming one of the user's groups and one of the door's zones whose schedule is active, and otherwise `no rule`. Codes are looked up by `auth.Service.CodeHash`. `checkCode` (`internal/app/checks.go`) carries out an allowed command through `newOverride`/`endOverride`, so it is pushed like any override change, logs it as a `command` event naming the commander (a command that cannot be carried out is logged and denied `command failed`), replies with the strike pulse of the door's effective configuration when allowed, and logs the check as an event; a reply that cannot be published makes the event denied `unreachable`. A check that cannot be handled (another protocol version, an unknown door, a store failure) is logged as `ignored a broker message` and gets no reply. The reason names live once, in `internal/event`.
- Events: `internal/event` holds the types (`check`, `command`, `open`, `alarm`, `update`), outcomes (`allowed`, `denied`, `alert` for alarms and failed updates, and `info` for updates sent or done, which the forced-open check, looking for `allowed`, never takes for an unlock), and reasons, and `event.Service` (`Record`, `Find`, a page of a filtered `connector.EventQuery`, which the store filters and pages). Events are only added (`EventsStore` has no update or delete); doors and users are soft-deleted so their events stay, and the deciding rule is kept by id alone. `GET /api/v1/events` (view-logs) filters by door, user, type, outcome, reason, and an RFC 3339 `from`/`to`, a page at a time; `/admin/events` (view-logs) does the same with dates read as whole days in the site timezone, builds its pager links and the user filter's × (which drops only the user) from the filters it read (`eventFilters.link`), never from the raw query, names a user filter it is given (from a user's or an event's link), clears every filter when one cannot be read and shows the first page keeping the filters when only the page number cannot, each with an alert. A check whose reply cannot be published is denied `unreachable` and keeps the rule that decided it. A door's and a user's page show their ten newest events (`recent`, the `recent-events` part) to viewers holding view-logs.
- Opening from the UI: `POST /api/v1/doors/{id}/open` and the door page's button (`POST /admin/doors/{id}/open`) publish an `open` command with the door's strike pulse through `controller.Service.Open` (409 `ErrOffline` while the controller is not connected) and log an `open` event naming the caller (denied `unreachable` when the command cannot be published, which answers 500). A route's `access` takes any one of several roles (`holding(roles...)`); `opensDoors` (manage-doors or door-commander) guards opening, overrides (API and pages), the door list and page, the door timeline, the door state and telemetry, and the live stream. A door commander without manage-doors sees the door page with its live state, overrides, who can enter, and the open card only (`doorContent.Manage`). `seesDoors` (opensDoors or manage-firmware) may read a door's page and load any door's pictures and thumbnails; a manage-firmware holder without opensDoors sees it read-only apart from the firmware card (`doorContent.Opens` false: no override actions, no open button, no timeline link, each explained in a note; its back link goes to the firmware page, `doorContent.Back`).
- Telemetry and door state: `internal/telemetry` (`telemetry.Service`). A door's controller publishes `Telemetry` on `doorcode/doors/<id>/telemetry` at its `telemetry_interval_s` and, outside open mode, `DoorEvent`s (`opened`, `closed`) on `doorcode/doors/<id>/event`; `(*App).handle` sends both leaves to `telemetry.Service.Receive`. Every report is stored as a sample (`TelemetryStore.AddSample`) and becomes the door's current state, the `StoredDoorState` embedded in its `StoredController` (`Telemetry`, the firmware version and signal, `DoorState` open or closed with `OpenedAt`, `LastSeenAt`), which the telemetry package writes only through `DoorsStore.SetDoorState`, so a concurrent rotate, revoke, or online change to the controller's hardware id or `Online` is never overwritten; any contact (telemetry, a door event, or an online message, the last in `controller`) clears `Unresponsive`. A door that opens when it was not open already is logged as an `alarm` event with outcome `alert` and reason `forced open` unless something unlocked it within its strike window (`DoorConfig.StrikeWindow`, its strike pulse plus its reply timeout) before: an `allowed` event at the door (a code, a command, a UI opening) or an open span of its timeline (open mode or an open override). The periodic work (`telemetry.Service.Sweep`) logs `held open` once per opening for a door open for its `held_open_s` (a door configuration field, pushed with the rest), marks a door unresponsive after the `unresponsive_minutes` setting without contact, only while the broker says it is online (an offline door is shown offline instead, and revoking a door's credentials clears the mark; deleted doors are left as they are), rolls up every hour that ended since the newest rollup (`NewestRollup`, `FirstSampleSince`, then one `AllSamples` read; each door's hour gets the mean, min, and max of signal, latency, and free memory and the total opens, `PutRollups` replacing), then removes samples older than `telemetry_retention_days` and rollups older than `telemetry_rollup_retention_days`. Rollup hours are UTC hours. `telemetry.Badges` is what door lists show of a door's state beyond online or offline (`Unresponsive`, then `Held open` or `Open`); a state change that changes the badges notifies the live hub for every page, any other a door-scoped `event: door` with the door's id. The door page shows a live state card to every viewer of the page (once a controller is enrolled), charts of signal and latency drawn as inline SVG by `chartFrame.chart` over `?range=` 6h or 24h (samples, the default 24h) or 7d or 30d (hourly means), and the door's ten newest alarms to view-logs holders. API (opensDoors): `GET /api/v1/doors/{id}/state`, `/telemetry` (samples, RFC 3339 `from`/`to`, the last 24 hours by default), `/telemetry/hourly` (rollups, the last 7 days by default).
- Firmware and OTA: `internal/firmware` (`firmware.Service`). Images are uploaded (UI form or multipart `POST /api/v1/firmware`, fields `version`, `notes`, `image`, at most `firmware.MaxBytes`, 16 MiB, read in memory like pictures) and stored as `bytea` behind `FirmwareStore` with their SHA-256 (hex), size, uploader, and upload time; versions are unique and made of letters, digits, `.`, `-`, `_`, `+`. Any file is accepted; `verify` in `internal/firmware/firmware.go` is the one place an image is judged before it is stored, where signature verification goes. The site default is a flag on the firmware row (`StoredFirmware.Default`, set only through `SetDefaultFirmware` and cleared through `ClearDefaultFirmware`, one at most by a partial unique index) rather than a setting, so the database holds it with the images and an environment variable can never name a version that is not there; a door's own firmware is `StoredDoor.FirmwareID` (set only through `SetDoorFirmware`, a foreign key that keeps it from being deleted); a door's target is its own or else the default. `firmware.Service.Plan` is every firmware and where every door stands (`DoorFirmware`: override, target, latest update, status `pending`, `updating`, `done`, `failed`, or empty for a door deleted, without a controller, or without a target); `Plan.InUse` refuses deleting the default or a version a door names. Each door's latest update is one `StoredUpdate` row (`PutDoorUpdate` replacing; version, command id, a SHA-256 of its download token, sent at, expires at sent plus the `update_timeout_minutes` setting, state `updating`, `succeeded`, or `failed`, finished at, detail). The periodic work (`firmware.Service.Rollout`) first fails every update past its expiry, then, while the update window (`update_window_days` `daily` or weekday names such as `sat,sun`, `update_window_start` HH:MM, `update_window_minutes`, read in the site timezone by `schedule.Expand` over the day before, so a window may run past midnight) is open, sends pending or failed online doors, in id order, their target until `update_concurrency` doors are updating; a door already sent its target in this window (failed) waits for the next one. Sending (`send`, also `UpdateNow` from `POST /api/v1/doors/{id}/update` and the door page, which ignore the window and the cap) draws 32 entropy bytes for a token and 8 for the command id, publishes `Command` `update` with `version`, `sha256`, and `url` (`public_url` setting plus `/api/v1/doors/{id}/firmware/{version}?token=`; nothing is sent while `public_url` is empty), stores the update, and logs an `update` event `update sent` (outcome `info`, naming the user for update-now). The download route is public (`anyone`) and serves the image only for the token of that door's update to that version while it is under way and not expired (403 otherwise). A door's update ends when its controller connects again reporting the version (`controller.Service.Connected` hook, `firmware.Service.Settle`: `update succeeded`, `info`), when it answers the command on `doorcode/doors/<id>/ack` with `result` `failed` (`Acked`: `update failed`, outcome `alert`, with its `detail`), or at expiry (`update failed`). Pages: `/admin/firmware` (manage-firmware: versions with running and targeting counts, upload, default, update window form over `settings.UpdateKeys`, rollout tables live over SSE), `/admin/firmware/{id}` (image, doors, delete), and a firmware card on the door page for manage-firmware holders once a controller is enrolled. API (manage-firmware): `/firmware` (list, upload), `/firmware/{id}` (get, delete), `PUT /firmware/default`, `GET /firmware/rollout`, `GET`/`PUT /firmware/settings` (only the rollout settings), `GET`/`PUT /doors/{id}/firmware`, `POST /doors/{id}/update`. The live stream also admits manage-firmware (`watchesLive`).
- Secret settings: a setting defined with `secret` (today `enrollment_password` and `oidc_client_secret`) is encrypted before it reaches the Store and decrypted only where the application needs its value (`settings.Service.Enrollment`, `ClientSecret`), in one place: `internal/settings/secrets.go` (AES-256-GCM, a 12-byte nonce from the Entropy connector, the setting's key as associated data, stored as `<nonce>.<ciphertext>` in base64url). The key is `DOORCODE_SECRET_KEY`, 32 random bytes in standard base64 (`openssl rand -base64 32`), read through the Environment connector; `app.New` refuses to start without a valid one, before migrating, because the enrollment password generated on first start and any client secret would otherwise be stored in the clear. Every listing (`List`, `Get`, the settings page and API) shows a secret as `settings.Mask` (`********`) when it has a value and empty when not, environment-provided secrets included (still read-only); the page offers it as a blank password field and the API marks it `secret`; an empty value from either leaves it unchanged, a value replaces it, and clearing empties it: the API's `{"clear": true}` (`settings.Service.Clear`; giving both or neither of `value` and `clear` is 400) and the page's Clear checkbox (`clear=<key>`, offered while the secret has a value, winning over a value typed beside it; `UpdateAll`'s `cleared`). A cleared secret is stored as the empty string, unencrypted, and reads as empty. A stored secret that cannot be decrypted (another key) fails only what reads it, naming the setting, and is fixed by storing it again.
- Settings page and theme: `settings.sections` lists each `Section` (name and about text, in display order: Site, Theme, Accounts and passwords, Single sign-on, Identity claims, Door enrollment, Telemetry, Firmware updates, Door defaults) once with the definitions it shows, each with a label and help (door defaults take the field's label and hint), and `definitions` is them in order, each given its section; `settings.Setting` carries them, and the page draws one card and one labelled table per section (Setting, Value, Source), a read-only setting showing its value and a note naming the variable that sets it. Theme colors are the settings `theme_accent` (`#rrggbb`, default `#4f39f6`) and `theme_accent_dark` (empty follows the accent), `settings.Current().Theme`; `base.html` writes them as `--accent` and `--accent-dark` in an inline `<style>` (`pageData.Theme`, absent on the error page, which reads no settings), and `ui/tailwind.css` mixes the whole `brand` ramp from `--brand` (the accent of the theme in use) with `color-mix`. The sign-in page picture is stored as `bytea` behind `SettingsStore` (`SignInImage`, `PutSignInImage`, `RemoveSignInImage`, one row of `sign_in_image`), prepared by `picture.Prepare` (the image rendition only) through `settings.Service.SetSignInImage`, served publicly at `GET /api/v1/sign-in-image` (`?v=` the Unix time it was stored, so `Cache-Control: public, max-age=31536000, immutable` is safe), shown behind the sign-in page's aside when set, and set or removed from the settings page (`POST /admin/settings/sign-in-image`, `/delete`) or the API (`PUT`/`DELETE /api/v1/sign-in-image`, admin, multipart field `picture`; `settings.ErrNoSignInImage` is 404).
- Displayed times: every instant a page shows is written by `shownAt(zone, t, layout)` in `internal/app/times.go`, in the site timezone, with one of the layouts named there (every page time and day layout lives in that file); templates use the `date` function (`{{date $.Zone .CreatedAt}}`, `pageData.Zone`). - Bulk import (manage-users): `internal/directory` `importfile.go` reads a CSV (`encoding/csv`, a UTF-8 byte order mark dropped, header names trimmed and lowercased, `user_id` and `groups` required, `email`, `first_name`, `last_name`, `expires_at` optional, any other or repeated column refused, at most `MaxImportBytes` 1 MiB (`ErrImportTooBig`, 413) and `MaxImportRows` 5000; problems with the whole file are `check.Problems` for the field `file`); `imports.go` plans each row (`PreviewImport`): the user id is required, a valid user id, and once per file; each slug in `groups` (separated by `;`, trimmed, repeats dropped) must name a group whose roles the importer holds; `expires_at`, on any row, is a date read in the site timezone or a row error; a user found by user id (`UserByUserID`) has the row's non-empty email, first name, last name, and expiry replace theirs (`Changes` names the columns that differ; when any does, the profile goes through the user form's checks with their own id, the importer may not make their own account expire now or earlier, and a changed email counts toward the file's email uniqueness; the display name is kept) and joins the listed groups they are not in (`update`, or `unchanged` when nothing changes), a deleted one is skipped; a user id nobody has with an email is created from the row (`create`): the email is unique in the file, the profile goes through the same checks as the user form, and the display name is the names or else the email; a user id nobody has without an email goes on the pre-assigned list of each listed group whose list lacks it (`preassign`, `Preassigns`; `unchanged` when every list holds it; a row with no groups is an error), so the person joins on first sign-in or whenever a user is created with it, and its names and expiry are not used. `ApplyImport` plans again and then applies row by row, creating users through `create`, the path `CreateUser` takes (pre-assigned groups and the listed ones in the one `CreateUser` store call), updating existing users through `UpdateUser` when the row changes them and adding them with `AddMember`, and pre-assigning with `GroupsStore.Preassign` (which leaves a list holding the id as it is); rows with problems are skipped. The Store offers no transaction, so a failure partway returns the rows applied so far (`Applied`), and applying the same file again is safe. Users so created have no code and no password. The server keeps nothing between preview and apply: the preview page carries the file in a hidden `csv` field that the apply form sends back, and the API takes the same file twice, so apply always reports against the directory as it is then. Pages: `/admin/users/import` (form, column help), `POST /admin/users/import` (multipart `file`: the preview, rows labelled and errors in red with each problem's column, totals, and an Apply import form only when something would change), `POST /admin/users/import/apply` (the result; a failure partway shows it with status 500 and an alert naming the request id). - Broker: Mosquitto 2 with its dynamic-security plugin. The driver, `internal/driver/dynsec`, uses `github.com/eclipse/paho.mqtt.golang` v1.5.1 (MQTT 3.1.1, QoS 1) over two connections as the broker's administrator, one for the application's messages and one for `$CONTROL/dynamic-security/v1` commands and answers; each client it creates gets a role of the same name carrying its topics (`publishClientSend` and `subscribePattern` ACLs, in which the plugin substitutes `%c`). Commands go one list at a time; each waits at most the timeout `Open` is given (`brokerCommandTimeout`, 10 seconds, in `cmd/doorcode`) for the answer carrying its correlation id, which the answer handler hands over through a one-slot channel, so an answer is never dropped for want of room; an answer that is not JSON fails the command waiting. `Open` closes both connections when either fails. The `misspell` linter knows the broker's name as a misspelling, so Go code calls it "the broker" and the driver is named after the plugin.
- MQTT protocol: `internal/protocol` holds the topics and the messages, and is the only package that uses the CBOR library, `github.com/fxamacker/cbor/v2` v2.9.1 (core deterministic encoding). Every message is a map with `v`, the protocol version (`protocol.Version`, 1); `Encode` sets it and `Decode` refuses another. Today: `Enrollment` (on `doorcode/enroll/<hwid>`, retained, `online`, `firmware_version`, `signal`; the last will says `online: false`; an empty payload is a cleared announcement), `Credentials` (on `doorcode/enroll/<hwid>/credentials`: `door_id`, `username`, `token`), `Online` (on `doorcode/doors/<id>/online`, retained, `online`, `username`, `firmware_version`, `signal`; the last will says `online: false` with the same username), `Command` (on `doorcode/doors/<id>/command`: `id`, `command`, and for `credentials` a `username` and `token`), `Config` (on `doorcode/doors/<id>/config`, retained: every field of `DoorConfig`, by the field names of `settings.DoorFields`), `Timeline` (on `doorcode/doors/<id>/timeline`, retained: `from`, `to`, and `spans`, each `start`, `end` in Unix seconds and `state` `open` or `locked`), `Check` (on `doorcode/doors/<id>/check`, which the server subscribes to as `CheckFilter`: `request_id`, `digits`, the code optionally followed by `*` and a keypad command), and `Reply` (on `doorcode/doors/<id>/reply`: `request_id`, `allow`, and `strike_ms` when allowed), `Telemetry` (on `doorcode/doors/<id>/telemetry`, subscribed as `TelemetryFilter`: `signal`, `latency_ms`, `uptime_s`, `free_bytes`, `firmware_version`, `reconnects`, `door_open`, `opens`), and `DoorEvent` (on `doorcode/doors/<id>/event`, subscribed as `EventFilter`: `event`, `opened` or `closed`). `Command` also carries `open` with `strike_ms`, and `update` with `version`, `sha256`, and `url`; `Ack` (on `doorcode/doors/<id>/ack`, subscribed as `AckFilter`: `id`, `result`, `failed` when the door could not carry it out, and `detail`). `Parse` reads a door topic's last level into `Topic.Leaf`; `(*App).handle` sends a check to `checkCode`, telemetry and door events to `telemetry.Service.Receive`, acks to `firmware.Service.Acked`, and everything else to `controller.Service.Receive`.
- Door controllers: `internal/controller`. A controller waits, pending, from its retained announcement until its last will, a cleared announcement, or approval; pending enrollments live in memory (`controller.Pending`) and come back from the retained announcements when the server subscribes again. Approval issues credentials (`door-<id>-<12 hex>`, a 24-byte base64url token; the store keeps only the username), allowed only `doorcode/doors/<id>/#`, publishes them to the controller, clears the retained announcement, revokes the door's earlier credentials, and takes the hardware off any other door. A door's online state comes from its online topic; connecting with a credential marks it used and revokes the door's older ones, and a last will of a revoked credential is stale and ignored. Deleting a door revokes its credentials (`controller.Service.Delete`). The periodic work (`(*App).Run`, at most once a minute by the Clock's `Alarm`) rotates a connected door's credentials once its newest are its `credential_rotation_days` old (the door's override or the `door_credential_rotation_days` default) and revokes all but the newest once those are `door_credential_grace_hours` old, sends timelines that are due again, removes expired sessions, watches the doors' state, and rolls firmware out; a part that fails does not stop the others, and their errors are joined. Run sets up the shared enrollment client (`enrollment_username`, `enrollment_password`; publish `doorcode/enroll/%c`, subscribe `doorcode/enroll/%c/credentials`, so a controller must connect with its hardware id as client id) on its first call; when the password is empty it generates one (18 entropy bytes, base64url), stores it, and logs it like the first administrator's, and fails to start only when it cannot store it (as when the environment sets it empty).
- Live updates: `GET /admin/live` (`watchesLive`, beside `livePages` in `pages.go` and built with `eitherOf` from opensDoors, manage-firmware, and `answersRequests`, the manage-users holders whose navigation counts the requests waiting) is a server-sent event stream that sends `event: requests` when access requests change (see access requests), `event: doors` whenever a door's status, its state badges, or the pending enrollments change, and otherwise `event: door` with `data: <id>` when only one door's state changed, such as on a telemetry report (`(*App).live`, a hub the controller and telemetry services notify; each listener's news waits in it until the stream takes it, and news of every door covers news of one). Pages that show such state (`livePages`, the dashboard among them, and only for a viewer `watchesLive` admits) include the `live` part, which loads `ui/static/live.js`; it opens the stream a `data-live-stream` element names and triggers `live-doors` (or `live-door-<id>`) on the body, and each live region reloads itself with `hx-get` of the page's own `URI`, `hx-select` of its id, and `hx-swap="outerHTML"`; the door page's state card listens for both.
- Static analysis and formatting: `go vet`; golangci-lint with govet, staticcheck, errcheck, errorlint, ineffassign, unused, unconvert, misspell, bodyclose, noctx; formatters gofmt and goimports (local prefix `github.com/dakriy/doorcode`). `make fmt` rewrites formatting.

The stub refuses references to schedules, zones, doors, or pictures it does not hold (`ErrNoSuchReference`), another door's picture as a primary one, nil picture data, and duplicate door and zone names ignoring case; deleting a schedule takes it off the zones in open mode during it, as the foreign key's cascade does, and deleting a picture clears the primary picture it was. `ExpireUser`, `DeleteUser`, `RevokeRoles` (ends every membership), `LeaveGroup`, `RemovePassword`, `ReplacePasswordHash` change a stored user by email. `FailRequests` fails the access requests aggregate and `FailRequestWrites` its writes; the stub refuses a request of a user it does not hold (`ErrNoSuchReference`). `FailEmailLookups` fails only `UserByEmail`, for a failure after a user id lookup succeeded. The sign-in page picture fails with `FailSettings` and `FailSettingWrites`, and `FailSignInImageReads` fails only `SignInImage`. `StoredCodeHash(email)` is a user's stored door code hash and `HashCode(code)` the hash of a code under the stored code hashing parameters, worked out in test support with argon2 independently of the application.

A setting is defined once in `internal/settings` (`definitions`), with an optional validator that both updates and `Current` apply. Its environment override is `DOORCODE_` plus the upper-cased key; a set variable (even empty) wins and makes the setting read-only.

The list of non-application directories lives once, in `scripts/scope.sh`; the coverage and mutation scopes are derived from it. The depguard and forbidigo file globs in `.golangci.yml` and the path regexes in `.golangci.connector.yml` mirror it and must change with it.

## Commands

| Command | Invocation |
| --- | --- |
| `verify-fast` | `make verify-fast` |
| `verify-mutation` | `make verify-mutation` |
| `verify-mutation-diff` | `make verify-mutation-diff BASE=<git ref>` (default `main`) |
| `verify-integration` | `make verify-integration` |
| `verify-all` | `make verify-all` |

`verify-fast` runs, in order: `go build ./...`; `go vet ./...`; `go vet -tags=slow ./test/connector/...` (integration compile); `golangci-lint run` and `run --build-tags=slow` (static analysis, formatting, import gates, effect calls, application complexity cap); `golangci-lint run -c .golangci.connector.yml` (connector complexity cap); `scripts/fast-tests.sh` (entrypoint suite with coverage, fast connector tests with connector coverage printed for information, coverage gate, runtime budget); `scripts/deadcode.sh`; `scripts/openapi-drift.sh` (OpenAPI drift gate: regenerates the document into `build/openapi.json` and fails when it differs from the checked-in `docs/openapi.json`); the dupl report. Make stops at the first failing step.

`make openapi` rewrites `docs/openapi.json` from the route table. Run it after changing a route, a wire struct, or an `apiDoc`, read the diff, and commit it. The entrypoint suite asserts the document's operations, statuses, and schemas by hand-written expectations, never by comparing with this file.

`verify-mutation` runs `scripts/mutation.sh`: gremlins with every optional mutator enabled and `--timeout-coefficient=100`, then prints every `LIVED`, `NOT COVERED`, and `TIMED OUT` line and fails if there is one. The log is `build/mutation.log`, the JSON report `build/mutation.json`. The run uses its own `GOCACHE` (`DOORCODE_MUTATION_GOCACHE`, default `~/.cache/doorcode-mutation-<checkout directory name>`, so worktrees never empty each other's) and empties it on exit, because per-mutant builds are never reused and would otherwise grow the shared build cache by gigabytes per run.

`verify-mutation-diff` runs the same script with `DOORCODE_MUTATION_BASE` set, so gremlins mutates only the lines changed since that ref (`--diff`), typically in seconds. It is the gate a change is developed against; the full `verify-mutation` runs once over a batch of changes before they reach `main` (see Deviations).

Runtime budget for `verify-fast` tests: 10 seconds (`FAST_BUDGET_SECONDS` in the Makefile), measured over both test invocations with `-count=1` so the cache does not hide the cost. Measured at bootstrap: about 0.7 seconds; after the foundation work about 0.6 seconds; after local sign-in and the UI shell about 1.1 seconds; after the route table, OpenAPI, and API tokens about 1.3 seconds; after users, groups, and roles about 2.1 seconds; after schedules about 2.2 seconds; after doors, zones, and pictures about 2.5 seconds; after building the OpenAPI document on first request and running entrypoint tests in parallel about 1.1 seconds (the prebuilt entrypoint test binary alone about 0.15 seconds wall, down from about 1.9); after access rules, overrides, and timelines about 1.5 seconds; after the broker connector and enrollment about 1.9 seconds; after door configuration and pushes about 1.4 seconds; after code checks and events about 1.45 seconds; after telemetry and door state about 1.35 seconds; after firmware and OTA about 1.7 seconds; after OIDC sign-in and secret settings about 1.4 seconds; after the user portal about 2.0 seconds; after access requests administration and bulk import about 1.6 seconds; after importing without email about 1.7 seconds; after the dashboard about 2.2 seconds; after the settings page, theme, sign-in picture, and EXIF orientation about 2.0 seconds; after the demo binary (no test changes) about 1.5 seconds; after zones carry access and open mode about 1.4 seconds.

The demo: `go run ./cmd/doorcode-demo` (or `-listen 127.0.0.1:8081`) starts with no Postgres or broker and prints the administrator's email and password; `docker build --target doorcode-demo -t doorcode-demo . && docker run --rm -p 8080:8080 doorcode-demo` does the same in a container. The Dockerfile builds both binaries (`CGO_ENABLED=0`, `-trimpath`, `-ldflags='-s -w'`) into an Alpine runtime as uid 10001, whose BusyBox `wget` answers the healthcheck on `/healthz`; the targets are `doorcode-demo` and `doorcode` (the default). `docker compose up -d --wait` runs the `app` service (the server) against the compose Postgres and Mosquitto once both are healthy, with `DOORCODE_SECRET_KEY` taken from the caller's environment or `.env` (empty when unset, so the app refuses to start but `docker compose up -d --wait postgres mosquitto` still works) and published on `DOORCODE_HTTP_PORT` (8080). README.md is the operator's guide: every environment variable, the OIDC addresses to register, enrollment, rollout.

`make ui` (`scripts/vendor-ui.sh`) rebuilds `internal/app/ui/static/app.css` with the pinned Tailwind CLI and re-vendors htmx and Swagger UI; run it after changing a template's classes or `internal/app/ui/tailwind.css`, and commit the result. It needs network access the first time. To upgrade a tool, change its version and every checksum in the script together, taking the checksums from the release's published sums (for Swagger UI, the SHA-256 of the npm tarball after checking it against the registry's published sha512 `integrity`).

Slow connector test prerequisites (record each new one here when the first slow test that needs it lands):

- **Postgres.** A disposable local PostgreSQL 18 whose URL is in `DOORCODE_TEST_DATABASE_URL`. `docker compose up -d --wait` starts one from `docker-compose.yml` (user, password, and database `doorcode`); then `export DOORCODE_TEST_DATABASE_URL='postgres://doorcode:doorcode@localhost:5432/doorcode?sslmode=disable'`. - **Mosquitto.** A disposable local Mosquitto 2 with the dynamic-security plugin, whose URL with its administrator's credentials is in `DOORCODE_TEST_BROKER_URL`. `docker compose up -d --wait` starts one from `docker-compose.yml`: `deploy/mosquitto/entrypoint.sh` creates the plugin's configuration on a new volume with the administrator `DOORCODE_BROKER_ADMIN_USERNAME` and `DOORCODE_BROKER_ADMIN_PASSWORD` (both `doorcode` by default) and lets it publish to `doorcode/#`; then `export DOORCODE_TEST_BROKER_URL='mqtt://doorcode:doorcode@localhost:1883'` (with `DOORCODE_MQTT_PORT` in place of 1883 when set). Each test uses topics and usernames of its own and deletes its clients, so the broker may be shared. Without the variable the slow Broker tests fail; they are never skipped. The production server connects with the same kind of URL in `DOORCODE_BROKER_URL`.

## Deviations

Intentional departures from the judgment rules, each with scope and reason.

- **Mutation gate per batch, not per commit.** A change is developed against `verify-mutation-diff` (the mutants on its own changed lines) and `verify-fast`; the full `verify-mutation` runs once over each batch of changes before it is merged to `main`, and `main` is never left with a surviving mutant. Reason: a full run takes about seven minutes at about 2200 mutants and reruns every mutant a change cannot have affected; the diff run covers the changed lines in seconds. Coverage stays at 100% on every commit.

## Known gaps

Gates the bootstrap could not establish for this stack, and what compensates.

- **Branch coverage.** Go reports statement coverage only. The coverage gate is 100% of statements; mutation testing (conditional negation and boundary mutants on every condition) is the compensating control for unexercised branches.
- **Effect calls through `net/http`.** The package cannot be denied wholesale, since the entrypoint needs it. forbidigo bans the listed client, listener, and file-serving identifiers by name; an effect reached some other way through `net/http` (for example a method on a value obtained elsewhere) is not seen. Review catches it.
- **forbidigo matches by text.** It runs without type analysis, so an aliased import (`t "time"; t.Now()`) evades the clock ban. Do not alias effect packages.
- **gremlins mutators.** gremlins does not mutate unary negation (`!x`), returned values, or removed statements. The entrypoint suite's outcome assertions are the compensation; review checks that weakening an assertion would make a test fail. gremlins also cannot attribute coverage to negative numeric constants or to `switch { case <expr>: }` conditions; mutants there stay `NOT COVERED`. Move the expression into a covered statement (negate a positive constant at use, name the boolean before the switch) rather than suppressing it.
- **Dead code in whole packages.** deadcode reports unreachable functions in packages it loads with `./...`; it does not see test-only reachability. `internal/testsupport` is filtered out because it is reached only from tests. An application package nothing imports is also caught by the coverage gate at 0%.
- **Connector-test `unused`.** The `unused` linter is off for `test/connector/` because the shared implementation tables are unused under whichever build tag has no tests of a given connector. Dead connector-test helpers are not detected.
- **Built stylesheet drift.** Nothing in `verify-fast` checks that the committed `app.css` matches the templates, since building it needs the downloaded Tailwind CLI. A class added to a template without `make ui` is simply unstyled. Review checks that a template change comes with a rebuilt stylesheet.
- **Response bodies against the document.** The spec test (`TestEveryDocumentedOperationAnswersWithADocumentedStatus`) checks that every documented operation answers with a listed status; it does not validate response bodies against their schemas. The schemas are derived from the same wire types the handlers encode, and the entrypoint suite asserts both by hand; review checks that a handler writes the type its entry documents.
- **Live script.** No test runs `ui/static/live.js` in a browser, nor the dashboard's htmx range swap. The entrypoint suite asserts the stream's events (`Browser.Stream`) and that live pages load the script; review checks the script and the live regions by loading a page while a controller enrolls.
- **Broker driver's failure paths.** The dynsec driver's command deadline, its handling of an answer that is not JSON or answers a command given up on, and `Open` closing the first connection when the second fails are not exercised by the connector tests, which cannot make the plugin answer badly or slowly or make one connection fail alone. Review checks them.
- **Identity driver's verification paths.** The fast Identity connector tests run the go-oidc driver against a local fake provider: discovery, the authorization address, the code exchange with PKCE and client authentication, ES256 ID token verification of a good token, userinfo, the end-session endpoint, and an unreachable issuer. They do not hand the driver an ID token with a bad signature, another audience, or an expired one, nor a provider whose discovered issuer differs from the configured one; go-oidc's verifier refuses those and the driver only passes its error on. No test reaches a real provider. Review checks the driver against a provider before a release.
- **Calendar script.** No test runs the browser script that draws a calendar (`ui/static/calendar.js`) or FullCalendar itself. The entrypoint suite asserts the occurrences the page lists in its table, from the same values the script reads; review checks the script by loading the page.
- **Stub time zones are the host's.** The `TimeZones` stub loads zones as the driver does, from the host's tz database or Go's embedded copy, rather than from fixtures; tests use zones whose rules for the dates they assert are long settled.
- **Demo.** No suite runs `cmd/doorcode-demo` or `internal/demo`; the entrypoint suite cannot import them and the demo stands in for systems rather than testing them. Review runs the demo after changing either, or after changing an API body or a connector interface the demo uses, and checks that it starts, the sign-in page answers, the simulated doors come online, and new events and telemetry appear (`/api/v1/events`, a door's `/state`). A compile error shows in `verify-fast`'s build; a seed the application refuses shows only when the demo starts.
- **CI.** The repository has no CI definition. When one is added, run `make verify-fast` and `make verify-mutation` on every change and `make verify-integration` on a schedule.
